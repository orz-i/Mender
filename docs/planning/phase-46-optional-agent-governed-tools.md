## Hard limitations

No currently installed Agent is modified automatically. The registered Agent workspace cwd stays independent of Sandbox, while governed **execution placement** optionally references a matching ready restricted local Sandbox. Host Agent cannot be configured for protected mode without an explicit eligible Agent resource; no hidden isolation upgrades. If a backend does not advertise ACP v1 HTTP MCP or has no viable credentials inside the limited process, it fails closed. Do not copy credentials or loosen Seatbelt to force success.

Production live Agent SQLite remains untouched by tests. Continue to preserve all unrelated `.agents/`, `.pi/`, `.intent-loop/`, `.commandcode/`. Code remains DDD/Clean Architecture: domain placement and owner service port independent of Agent protocol, bootstrap composes canonical governance capabilities, ACP adapter handles protocol conversion only. This phase must not become a new Agent Harness.

## Implementation and acceptance — 2026-10-17

This phase preserves the Phase 45 backend-neutral ToolSupply design. It does **not** make every Agent require a Sandbox, automatically change an existing Host Agent's isolation, or grant a Profile additional capabilities.

- **A / `a8d790c`**: ADR-0052 established optional placements for each registered Agent working directory, with separate Sandbox registration and exact ToolID selection. Documented default-off and hard-failure semantics, lifecycle and UI.
- **B / `134a69d`**: forward-only Agent SQLite **v11** `agent_tool_placements` with one owner configuration per AgentID/workspace alias, canonical root, owner-chosen ready restricted local Sandbox, sorted existing ToolID set, and last-updated timestamp. Historical v6/v7/v8/v9/v10 migration tests preserve their intended synthetic versions. The v11 trigger forbids removing a workspace while its governed placement still references it. No user Agent, ToolID or historical Task is rewritten.
- **C / `54d3068`**: owner-only Runtime list/configure/disable and task runtime resolver. Configuring checks `Agent.isolation=restricted_host`, same canonical root and owner as the selected existing ready restricted local Sandbox, prepared pinned Workspace Tools, source keys limited to `workspace.read/search/edit`. The task resolver runs only after durable Task admission and `running` transition. Missing placement supplies **nothing** (original task behavior); stale or invalid placement fails the Task explicitly without a Host fallback. Each issued token is owned by the active Task, carries an exact immutable placement snapshot, rechecks current placement and Profile/Sandbox/Tool grants on every InvokeTool, and expires on disable/change/cancel/Task end/restart. No new Providers or Tools are created.
- **D / `c6283c6`**: Wails local-owner-only configuration methods, typed SDK/desktop binding (the ordinary HTTP client rejects mutations), and focused **Agent → Governed tools** view. For each default or additional registered workspace, a preview shows enabled/disabled status; an explicit modal lists only matching ready restricted local Sandboxes, with prepared existing read/search/edit tools. Saving or disabling is explicit; no forms are placed on the listing; Host Agent shows its eligibility limit. The Profile-exposed Agent Delegation facade remains exactly four tools.
- **Edge / `b319b1d`**: atomically prevent removing an additional workspace with an active governed placement, and expose the stable `agent_workspace_governed_tools_enabled` conflict in Chinese rather than “unexpected error”. Removing a normal unconfigured workspace remains unchanged.
- **Lifecycle / `d8dba2e`**: Task cancellation during ToolSupply acquisition now goes through the existing Task cancelled/unknown transition logic and does not launch any Agent subprocess. A missing/unavailable configured placement remains an explicit failed task diagnostic, never a silent Host fallback.

- Tests separately prove a generic restricted macOS synthetic ACP process is denied native writes to its admitted protected root, while approved Mender `workspace.edit` and `workspace.read` operations succeed through the canonical Invocation/Policy/Sandbox Router. This is NOT universal mandatory isolation of arbitrary host files or networks.

### Real restricted Agent execution acceptance — live gate (2026-10-17)

This is the next **verification gate of Phase 46**, not an expanded Agent Harness or a new phase. Start with an entirely disposable Mender SQLite, restricted Agent, matching ready local restricted Sandbox, prepared existing Workspace read/edit ToolIDs, a dedicated Profile with explicit ToolBindings, Sandbox Read/Edit grants, AgentGrant and an explicit owner-configured placement. Keep `workspace.shell` unselected. The Task prompt is bounded to an owner-created disposable file; verify the actual canonical invocation Audit and exact file contents, not just Agent prose. No real project edits, user credential reading/copying, production grants or silent Host fallback.

1. **No-prompt readiness first**: inspect local ACP v1/HTTP support and whether a real CLI can open a session under the actual Seatbelt `restricted_host` process plan. Do not assume the Host CLI's authentication status persists under isolation. Missing authentication/credentials or unsupported ACP MCP must be reported as a concrete block; never loosen filesystem/network confinement or inject user credentials to make tests pass.
2. **Positive real Task only if ready**: submit one intentionally short, explicitly granted Profile Agent Task through the normal durable Task lifecycle. Demand one Mender `workspace.read` and one Mender `workspace.edit` in the temporary root; verify the file bytes and audit events. Native root writes must fail without the governed Tool path. Bound runtime and record terminal Task state and exact stage of any failure, without logging secrets or raw prompts.
3. **Negative lifecycle after positive**: revoke Profile ToolBinding/AgentGrant or disable placement and assert the issued task capability becomes unusable; no replay and no fallback. The previously accepted synthetic tests remain an independent regression gate, not a substitute for the real Agent result. Record which backend and capability negotiation was actually observed, including failures.

Do not claim authenticated real-Agent acceptance unless the real CLI demonstrably invoked canonical Mender tools while root-native write attempts were constrained. Actual owner GUI acceptance is already closed separately above.

#### Operator evidence — startup blocked before ACP initialize

- Opt-in real CLI readiness probes use the **same production `LocalFactory.CommandWithConfig` + macOS Seatbelt `restricted_host`** path and do not send any model prompt. Both installed candidates (`opencode v2.0.30`, `grok v1.0.62`) exited before returning an ACP `initialize` response with the protected root read-only. - **Non-governed diagnostic controls**, explicitly without a Task tool bearer, confirmed that both CLIs advertise ACP v1 HTTP when launched on the same machine in Host mode. Even an ordinary `restricted_host` control with a writable disposable root exited before ACP initialize for both candidates; the failure is **not caused only by** Phase 46's extra protected-root write restriction. The diagnostic Host control is **not** a fallback path for governed tasks.
- An explicit, strictly bounded (50-second max) disposable-runtime real Task smoke created a fresh SQLite, restricted Sandbox and prepared canonical Workspace read/edit ToolIDs, exact Profile bindings, Sandbox Read/Edit grants, AgentGrant and owner placement.
