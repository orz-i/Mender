## Preserved invariants

- Profile/Tool identity, exact Skill installation membership and existing
  policy, credential, concurrency and reference guards remain authoritative.
- Delivery configuration cannot authorize a Tool outside Profile membership.
- Changing MCP configuration does not change the selection revision or rewrite
  existing Skill files/exports. A membership change does not silently publish a
  replacement local artifact.
- CLI recipes and exported packages remain explicit snapshots. Only resources
  with actual managed lifetimes retain runtime state.
- Historical unowned Skill deployments remain unowned; queries do not adopt or
  remove them. Content/digest/trust/drift ownership stays with Skill.
- No migration starts a Server/Tunnel, writes Skill files or expands grants.
- R6 capability/client/feature restructuring is not included.

## Verification and upgrade

Use nonempty legacy fixtures for all three MCP modes, Tunnel references,

The migration is forward-only. Real upgrade requires a consistent shared-DB and
managed-resource backup, stopped writers, and testing a disposable restored copy
before deployment. Restoring the old binary alone is insufficient; recovery
must restore the matching backup and reconcile any writes made after upgrade.

## Implemented ownership and contract changes

- `profile/application/delivery` owns Profile Skill preflight/revision fencing,
  reverse compensation, ownership checks, CLI recipe and Agent Plugin snapshot
  orchestration. `profile/infrastructure/localdelivery` supplies host metadata.
  Skill still owns content, trust, digest, drift and deployment records.
- `mcp/infrastructure/managed` owns Profile-managed listeners, Tunnel processes,
  immutable HTTP snapshots, metadata fingerprints and lifecycle state. Runtime
  composes callbacks once and closes the manager. The separate Agent Task-token
  MCP proxy remains an Agent execution adapter.
- `mcp/domain.Config`, `mcp/application/delivery` and MCP SQLite own explicit mode,
  Tunnel and hybrid direct selection. Selection/configuration writes use two
  independent revision fences. Current Profile membership is rechecked at the
  SQLite commit point; removing a member prunes its direct selection and advances
  the delivery revision. Unchanged members are upserted rather than deleted and
  reinserted, preserving independently owned selections.
- Profile schema **7** and MCP delivery schema **1** are recorded in the same
  transaction as the historical conversion and removal of `exposure_mode`,
  `tunnel_id` and binding `direct`. Existing table identities, indexes and
  foreign-context guards remain intact. Existing Tunnel deletion guards are
  installed before that transaction publishes the handoff.
- HTTP `GET/PUT /profiles/{slug}/mcp-delivery` exposes `profileRevision` and the
  independent configuration `revision`. PUT requires `expectedProfileRevision`;
  missing `expectedRevision` is create-only, while a supplied value (including
  zero) is a CAS update. Missing configuration is a specific 404; SDK/Wails expose
  it as nullable data without swallowing an unknown Profile or other errors.
- Profile create/tool DTOs no longer accept mode/direct, Profile output omits
  mode/Tunnel/direct, and the old Profile Tunnel endpoint is retired. CLI now
  configures MCP through `profile mcp-delivery show/configure`; Wails, SDK and
  generated contracts switch together. Profile pages retain members/governance;
  the MCP delivery page owns explicit projection/Tunnel settings and versions.
- Managed HTTP refresh fences Profile, delivery and Catalog revisions before
  publication. Delivery changes refresh projections without restarting listeners
  or Tunnels; visibility and authorization remain distinct. Existing stdio
  startup snapshot semantics and explicit local artifact updates remain intact.
