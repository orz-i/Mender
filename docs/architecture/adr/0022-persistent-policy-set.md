# ADR-0022: Persist an unordered PolicySet with deterministic most-restrictive evaluation

- Status: Accepted
- Date: 2026-09-27

## Context

Mender currently has a canonical Policy decision type but no editable Policy model.

The Runtime always composes the local AllowAll evaluator, which returns allow with reason local.default. Profile ToolBinding may then tighten that decision with require_approval or deny.

Phase 9 established the execution position for Policy:

~~~text
Resolve scope
  -> resolve Tool
  -> validate arguments
  -> derive Governance Facts
  -> evaluate global Policy
  -> apply Profile ToolBinding constraint
  -> Approval
  -> Execution Guard
  -> Executor
~~~

Phase 12 needs editable global Policy without introducing rule-order bugs, adapter-specific authorization, or a DSL whose meaning changes when rows are reordered.

Ordered first-match rules are dangerous for a governance product because a broad allow moved above a narrow deny can silently weaken enforcement.

## Decision

Mender introduces one persistent PolicySet.

~~~text
PolicySet
  DefaultDecision
  Rules[]
~~~

DefaultDecision is one of allow, require_approval, or deny.

A Rule contains:

~~~text
Rule
  RuleID
  DisplayName
  Enabled
  Decision
  Match
  CreatedAt
  UpdatedAt
~~~

RuleID is generated by Mender and is not a normal-user input.

### Initial migration behavior

A new Policy store is initialized with DefaultDecision=allow and no Rules.

This preserves the execution effect of the current local AllowAll default.

The stable default reason changes from the infrastructure placeholder local.default to policy.default.allow only after the configured evaluator is installed.

### No rule priority or ordering

Rules have no priority field and no semantic order.

The repository may return rules in a stable presentation order, but evaluation never depends on row order, creation time, UI order, or database order.

### Matching and decision composition

Disabled rules never match.

All enabled matching rules contribute a decision.

If no rule matches, the evaluator returns DefaultDecision.

If one or more rules match, DefaultDecision is not part of the combination. Matching rules are combined by:

~~~text
allow < require_approval < deny
~~~

The most restrictive matching decision wins.

This gives two important properties:

1. a deny rule can never be overridden by another rule;
2. default-deny allowlists remain possible because an explicit allow rule is evaluated instead of the default when it matches.

Examples:

~~~text
default allow + no match -> allow
default deny + no match -> deny
default deny + matching allow -> allow
matching allow + matching require_approval -> require_approval
matching allow + matching deny -> deny
matching require_approval + matching deny -> deny
~~~

A broad deny therefore cannot contain a narrow allow exception. Users should model allowlists with default deny plus positive allow rules rather than deny-all plus exceptions.

### Deterministic reason selection

When multiple matching rules have the same winning decision, the evaluator selects the lexicographically smallest RuleID as the decision reason source.

Stable rule reason codes use policy.rule plus the stable generated RuleID suffix.

Default reason codes are policy.default.allow, policy.default.require_approval, and policy.default.deny.

Audit continues to store only effective decision kind and reason code, not the complete matched-rule set.

### Profile ToolBinding remains a second tightening layer

The configured global Policy decision is evaluated first.

Profile ToolBinding PolicyConstraint is then applied using the existing most-restrictive rule:

~~~text
global Policy decision
        +
ToolBinding constraint
        ↓
effective execution decision
~~~

ToolBinding still has no allow value and therefore cannot weaken either a global rule or the global default.

### Approval remains separate

Policy may return require_approval, but Policy does not perform approval.

The existing ApprovalGate remains the authoritative next stage.

Until an interactive approval adapter is implemented, require_approval continues to fail closed through RejectApproval.

The management UI must communicate this accurately.

### Persistence

Policy owns a forward-only SQLite schema.

The store persists the singleton default decision, Rule identity/display/enabled/decision, serialized non-secret Match state, and timestamps.

Unknown future schema versions fail closed.

Malformed persisted decisions or matchers fail closed during restore.

### Management semantics

Default decision and individual rules are edited through targeted application use cases.

Mender does not use whole-document blind replacement for normal management because concurrent edits to unrelated rules should not silently overwrite each other.

Normal UI never asks for RuleID. RuleID is generated internally and appears only as secondary metadata/API identity.

## Alternatives considered

### Ordered first-match rules

Rejected because row ordering becomes an authorization primitive and accidental reorder can weaken security.

### Numeric priority

Rejected for the same reason. Priority values are difficult to reason about and create hidden interactions between otherwise independent rules.

### Include DefaultDecision in every combination

Rejected because default deny would make explicit allow rules useless and prevent allowlist policy.

### Last-write-wins

Rejected because persistence order has no security meaning.

### ToolBinding policy replaces global Policy

Rejected because Profile configuration would become a privilege-escalation path.

## Consequences

### Positive

- evaluation is deterministic and independent of UI/database ordering;
- deny rules are monotonic and cannot be overridden;
- default-deny allowlists remain expressible;
- ToolBinding continues to be a tightening layer;
- Audit retains one stable bounded reason code;
- existing execution behavior migrates without an immediate allow/deny behavior change.

### Negative / trade-offs

- deny rules cannot have allow exceptions;
- users must understand that DefaultDecision applies only when no rules match;
- require_approval is configurable before an interactive approval workflow exists and therefore currently fails closed.

## Follow-up

ADR-0023 defines the bounded Match language and the treatment of unknown Governance Facts.
