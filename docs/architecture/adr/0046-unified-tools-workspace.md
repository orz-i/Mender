# ADR-0046 — One Tools workspace; keep Provider and Catalog distinct

- Status: Accepted
- Date: 2026-10-16
- Refines: ADR-0039, ADR-0045 and the Phase 2 Catalog contract

## Problem

The current sidebar separately advertises Provider and Catalog. Providers are *configured sources of canonical Tools*, not installed Plugin Packages. The global Catalog is a flat Tool listing and cannot communicate the real Agent/Sandbox owner of a host-managed Provider facade. The Marketplace also offers provider creation, duplicating the user-facing Provider picker. Catalog browsing fetches only 100 Tools and search 30 before client pagination; Profile selection can silently omit matching Tools beyond the first bounded slice.

## Decision

1. **One Tools entry, two levels, not two technical tabs (2026-10-16 refinement).** `/tools` shows the services/integrations the user added as a single uniform card list: e.g. **AnySearch**. Select a card to enter `/tools/:providerId`, listing *only that service's Tools*. The selected service is the visual owner regardless of its hidden Provider driver; no standalone `Provider` vs `Catalog` vs `internal/external` tab or filter. Deep-linked Marketplace `Connect/Create` enters `/tools?create=1&offeringId=…` or `pluginId=…` and opens the relevant focused form. Existing `/providers`, `/catalog` routes and temporary `view=sources|catalog` presentation are retired, not bridged. The workspace remains one information topic per viewport, with an in-context Back to tools action.
2. **Do not merge persistence or implementation identity.** Keep `catalog.Provider`, `catalog.Tool`, `provider_configs`, `ProviderID`, `ToolID`, `(ProviderID,SourceKey)`, native package installations, tool synchronization, invocation and Policy/Profile governance unchanged. One plugin installation can back many configured Providers. No `sources` table, alternate inventory or Agent loop.
3. **One uniform source identity to users; exact Host attribution under the hood.** AnySearch is the **AnySearch** service even though its executor is a configured MCP Provider. The existing user-selected `displayName` is the service's primary presentation, and canonical ProviderID identifies the instance; no new resource table or redundant installation record. Tool cards/drilldown link by that ID. The Host still derives Agent/Sandbox owner relations from `agent_tool_facades`, `sandbox_tool_suite_bindings`, `sandbox_job_suite_bindings` and authentic resource names. Show **all** sources in the same list, including Agent/Sandbox-backed Tools, without `internal/external` toggles or exposing `pluginId` as the primary label. An orphaned managed facade remains visible with a neutral diagnostic, not a guessed owner; never mutate bindings on reads. Edit/auth/sync/delete continue only for independently configurable sources, while resource-owned sources offer `Manage` at the owning Agent/Sandbox. These operation guards do **not** become end-user classification choices.
4. **Tool catalog is complete, Profile exposure stays separate.** Browse supports opaque continuation cursors and a reliable end marker in HTTP/OpenAPI/TS SDK/Wails; Provider filter is applied by the backend. Lexical search supports the same bounded continuation (stable BM25 order and ToolID tie-break), not client slicing of only the first 30/100. A small monotonic Catalog Tool revision maintained transactionally by SQLite triggers invalidates cursors after Tool insert/update/delete. Cursor includes request scope, revision, offset and (for Profile-scoped search) the immutable allowed-ToolID digest; invalid/stale or cross-scope cursors fail closed. Revision is internal Catalog metadata, **not a second inventory**. Catalog can render many pages without loading full Tool schemas. Profile Tool Picker uses the same source-filtered, paged discovery contract, retains already-bound ToolIDs across pages, and does not automatically grant a Profile.
5. **Status and ownership are different dimensions.** The Catalog may display source ownership and verified Profile binding information; it must not claim reachability or execution authorization merely because a Tool is synchronized. Catalog browsing never probes upstream endpoints, activates plugins or resolves credentials. The governance chain remains Principal/Profile ToolBinding → Policy/Approval → Resource grants/lease/budget → Executor → audit. No cross-agent/Sandbox mixing.
6. **Product intent, not leaked implementation.** Marketplace = discover/install/connect; Tools home = installed/configured services such as AnySearch, Agent/Sandbox tool providers and other registered capabilities; source detail = the selected service's canonical Tools; Profiles = explicit supply. Package installations remain Marketplace Installed; managed facade operations still belong to their Agent/Sandbox resource owners. No new permanent route aliases, client-side shadow source registry, or forced explanation of Provider to the user.

## Invariants / acceptance

- One sidebar Tools item with **two navigation levels**: services on `/tools` (AnySearch as a named card), and its Tools on `/tools/:providerId`. No internal/external toggles, no Source/Catalog tabs. Marketplace and resource links use the exact service/owner routes. Unsupported former paths do not mount duplicate management pages.
- MCP, OpenAPI, Model Tools and approved AnySearch create focused Sources; no generic internal Provider create/edit/sync/delete bypass. Plugin installation lifecycle remains on Marketplace Installed.
- All sources share the same card layout. AnySearch does not appear as `MCP Provider` or `io.mender.provider.mcp`; drilldown lists only its ToolIDs. Agent/Sandbox entries show verified owner and navigate to it for management; orphaned facades show neutral diagnostics. Canonical IDs and existing Profile assignments never change.
- Paginate over >100 Tools for browse and search, including Provider-scoped, Profile picker and zero/invalid cursor cases; tie-break deterministically. No phantom availability claims or side effects on read.
- HTTP, CLI as relevant, SDK, Desktop Wails bindings and shared React UI agree. All Go/TS tests, generation drift, i18n, lints, build and security gates pass, with tracked worktree clean.
